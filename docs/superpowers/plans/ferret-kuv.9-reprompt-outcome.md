# ferret-kuv.9 — Re-prompt friction vs pivot outcome signal — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** DRAFT — dk approves before any code. The bead is `has_design_questions=true`; the **Open Questions** section below MUST be resolved (esp. Q1 scoring framing and Q4 embedding source) before implementing Task 3+.

**Goal:** Mine the "no, do X" correction signal ferret discards today: pair adjacent user prompts, score each pair by normalized edit-distance × semantic-similarity, and split the two outcomes — high-edit+high-sim = *friction* (struggling to be understood), low-sim = *pivot* (a new task boundary).

**Architecture:** Deterministic, reference-free, LLM-free Go scorer in a new `internal/score/` package (per shared-design Decision 2), reading user-prompt text retained in the `Event` artifact (per shared-design Decision 1). Friction surfaces as a `Kind=friction` `Finding` (Decision 3); the pivot verdict is emitted as a boundary HINT for kuv.2 segmentation — kuv.9 does **not** rewrite segmentation. Edit-distance is in-repo arithmetic; semantic similarity is the one open dependency (see Q4).

**Tech Stack:** Go (stdlib + existing ferret packages), kong CLI, table-driven tests (ADR-008). No new module dependency without dk sign-off on Q4.

## Approach

Three layers, built bottom-up so each is independently testable:

1. **Retain prompt text** (D1) — the load-bearing precondition. Without the human's words in the artifact, there is nothing to score. Pure schema + ingest change; verifiable by re-ingesting a fixture and asserting `Event.Text` is populated and capped.
2. **The scorer** (`internal/score/reprompt.go`) — pure functions over adjacent prompt-text pairs: `normEditDist(a, b) float64` (in-repo Levenshtein, normalized to [0,1]) and `similarity(a, b) float64` (see Q4 — start with a deterministic lexical proxy; embedding cosine is gated on Q4). A `Classify(pairs) []RepromptVerdict` maps each pair to `friction | pivot | neither` using thresholds (Q2). All deterministic, table-tested.
3. **Surface it** — (a) a `ferret reprompt` subcommand (mirroring `conformance`) that runs the scorer over a session and prints friction pairs + pivot hints in text/JSON; (b) wire friction into `Finding` as `Kind=friction` (D3) so it appears in `ferret report`; (c) emit pivot verdicts as a boundary hint for kuv.2 (Q3).

**Why lexical-first for similarity:** ferret has NO embedding pipeline today (`embed-pipe` risk marker; decode.go/analyst hits are incidental). A true embedding dependency is itself a design call (Q4) AND arguably violates the LLM-free invariant. Building the scorer against a `similarity` *interface* with a deterministic lexical default (e.g. token Jaccard / cosine over bag-of-words) lets the whole pipeline ship and be validated, with embedding cosine slotting in later behind the same interface if dk approves. This keeps Task 2 unblocked while Q1/Q4 are open.

## Open Questions (for dk — REQUIRED; bead is `has_design_questions=true`)

**Q1 — Scoring framing is UNGROUNDED (blocks reliance on Task 2 thresholds/semantics).**
kuv.11 REJECTED arXiv:2510.09801 (PULSE) — it contains no re-prompt / edit-dist / semantic-sim analysis. The heuristic survives only as an engineering proxy and must be re-grounded in the query-reformulation literature (Amazon contextual-rephrase; the 2024 conversational-search 18-pattern follow-up taxonomy) before the scoring is trusted. **Decision needed:** (a) is the engineering-proxy framing acceptable to ship v1 behind, with re-grounding tracked as follow-up, or (b) must re-grounding land first? And which source, if any, may be cited in code? (Plan currently writes NO paper citation for the friction/pivot heuristic — only textbook Levenshtein — pending this.)

**Q2 — Distinguishing FRICTION from PIVOT (the bead's headline design question).**
The whole signal hinges on the friction/pivot split, and the boundary is genuinely fuzzy:
- **friction** = high edit-distance + *high* similarity (same intent, reworded because misunderstood)
- **pivot** = *low* similarity (a deliberate new task)
But three confounds need a ruling: (i) a *short clarifying add-on* ("...and also lint it") is high-sim + moderate-edit but is neither friction nor pivot — where does the `HighEdit` floor sit? (ii) a *deliberate refinement* ("make it blue instead of green") is high-sim + high-edit yet is healthy iteration, not friction — does edit×sim alone separate "frustrated re-ask" from "normal refinement," or do we need a confound like elapsed-turn-count / an explicit negation cue ("no", "not", "instead")? (iii) what are the concrete default thresholds `HighEdit / HighSim / LowSim`? Proposed starting point pending dk: `HighEdit=0.5, HighSim=0.7, LowSim=0.3` — needs validation against a labeled fixture. **This is the question the bead flags; v1 thresholds should not be hard-trusted until dk rules.**

**Q3 — Pivot-hint consumption contract + artifact vs raw-transcript impedance mismatch.**
D1 says read prompt text from the `Event` artifact. But `cmd/ferret/segment.go` (the pivot-hint consumer) does NOT read the artifact — it re-reads raw transcripts via `transcript.ReadLines`/`promptText` and already has its own thinking-side `pivotCues`. So kuv.9 (artifact-sourced) and kuv.2 (transcript-sourced) live on different ingest paths. **Decision needed:** how should the pivot hint actually reach segmentation — (a) kuv.9 emits JSON that a later kuv.2 pass reads (loose coupling, plan's default), (b) move segmentation onto the `Event.Text` artifact path so both share one source (larger, touches kuv.2 — out of this bead's "do not rewrite segmentation" scope), or (c) defer the feed entirely and ship only the friction half now? Plan currently assumes (a) and stops at emitting pivot verdicts in `ferret reprompt --format json`.

**Q4 — Semantic similarity source (the `embed-pipe` risk).**
The DESCRIPTION says "embedding cosine," but ferret has NO embedding pipeline, and a real embedding call arguably violates the epic's LLM-free engine invariant (embeddings are model output). **Decision needed:** (a) ship the deterministic lexical proxy (token Jaccard / bag-of-words cosine) as the `SimFn` default — plan's choice, keeps `score/` LLM-free and unblocks everything — and treat embedding cosine as a future analyst-side `SimFn`; (b) adopt an embedding dependency now (which model/source? local vs API? this is itself a design call); or (c) something else. Plan builds against a `SimFn` interface so either path slots in without rework, but defaults to (a).

**Q5 — Does friction need to ride the `Finding` model at all (D3 + YAGNI)?**
The Done signal accepts the friction flag appearing in `ferret report` **OR** a new subcommand. If the `ferret reprompt` subcommand satisfies it, D3 + YAGNI say skip the `Finding` field churn entirely. **Decision needed:** is `ferret report` integration wanted for v1, or is the standalone subcommand sufficient? Plan defaults to subcommand-only and treats the `Finding` wiring (Task 3 Step 7) as optional/skippable.
